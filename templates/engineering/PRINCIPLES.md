# Engineering principles

One set of principles for every product: architecture, code, tests, AI routes, privacy and
speed. The design standard (`templates/design/STANDARD.md`) covers screens and UI copy; the
writing policy (`POLICY.md` §16) covers how agents report. A product's `docs/PRINCIPLES.md`
points here and adds only what is its own.

The short version: one source for every fact, logic below the screen, a typed contract at every
edge, a test for every change, and a gate on the laptop that says no.

## How this file works

- **At most 15 active principles.** A principle is an `### E<n>.` heading above "Retired or
  advisory". A new one displaces the weakest, in the same PR.
- **Every principle carries a date, a scope and a check**, directly under its heading:
  `Since <date> · Scope: <where> · Check: <how>`. The check names a command that can say no
  (`./check.sh`, a script, a test, `teyla ux check`). `review` is allowed only where no command
  can judge it, and then the principle says what the reviewer looks for. The check here is what
  each product's gate must run; a product that has not built it yet marks it "pending" in its
  `docs/PRINCIPLES.md`, with the session or PR that will build it.
- **A ratchet, not a ban, for old code.** Where a principle arrives after the code, the gate
  counts the violations and the count may only fall (a `FONT_CEILING=167` line in the product's `check.sh` is
  the pattern). New code meets the principle from the first commit.
- **Where the rules come from:** Apple's HIG and the platform docs; Vercel Geist and Linear for
  one source of truth and speed as a feature; the eval-driven practice of AI-native teams
  (OpenAI and Anthropic eval guides); Codex and Grok second opinions of 2026-11-25. Codex's
  warning is the reason for E3's last sentence: green gates and three agreeing engines can still
  repeat the same wrong assumption at speed.

## Part 1. Architecture

### E1. One source for every fact; every copy is generated, and a stale copy is red
Since 2026-11-25 · Scope: tokens, schemas, API types, project files, string tables, docs that list code · Check: each generator has a `--check` mode that `./check.sh` runs

A value is written in one place. Tokens generate platform files (DTCG → Swift, CSS, Kotlin);
a schema generates types and clients; `project.yml` generates the Xcode project. Never edit a
generated file; never commit what a generator can rebuild unless the gate compares it. A doc that
lists code (a component table, a feature list) is checked against the code.

### E2. Logic lives in the engine; the screen renders what the engine returns
Since 2026-11-25 · Scope: every product with a UI · Check: the engine package has no UI framework import (a grep in `./check.sh`); review for derivations in views

Dates, ordering, grouping, conflicts, counts and "what is next" are computed in one engine
package, with tests. A view formats and lays out. A derivation found in a view moves into the
engine the day it is found, with its test. A second platform calls the engine or its twin; it
never re-derives.

### E3. Twin implementations answer from one sheet, and the sheet is checked by a person
Since 2026-11-25 · Scope: products with more than one engine (Swift, TypeScript, Kotlin) · Check: each twin's test diffs its output against the committed conformance sheet

The answer sheet is generated by the primary engine from a fixture and committed. Every twin
must reproduce it byte for byte. Keep one pleasant fixture and one deliberately awkward one
(time zones, overnight moves, cancellations, missing fields). A change to the sheet is read by a
person in the PR: three engines can agree on a wrong answer.

### E4. A typed, versioned contract at every edge
Since 2026-11-25 · Scope: documents, API calls, database rows, AI outputs, deep links · Check: schema validation tests; generated types `--check`; a decode test per stored version

Every document names its schema version (`<product>.<thing>.v1`). A reader decodes every
version still on a device. Database types and API clients are generated, not hand-written.
Ids are stable strings and never renumbered. A model's output is decoded into a type and
validated before anything reads it.

### E5. One real-world fact is one record; every write is idempotent
Since 2026-11-25 · Scope: imports, AI intake, sync, retries, shared edits · Check: an engine test per import path: the same source twice yields one record; a retry changes nothing

A booking is matched by its natural key (reference, provider, dates, place) before a new item is
created. Importing the same file twice, retrying a request or replaying an offline queue never
duplicates an item and never loses an edit. A duplicate the person sees is a data bug, not a
display bug.

## Part 2. Code and tests

### E6. Every change ships with the test that would have caught it
Since 2026-11-25 · Scope: engine, backend, scripts · Check: a pre-push step fails when engine or backend sources change and no test file changes in the same diff

A feature gets a test of its behaviour; a bug fix gets the failing case first. A UI change gets
a screenshot in the PR and, for a critical path, a UI test. "Covered by existing tests" names
the test.

### E7. The laptop is the gate: one command, the same as the deploy
Since 2026-11-25 · Scope: every repo · Check: `./check.sh` exists and `.githooks/pre-push` runs it (`git config core.hooksPath` is `.githooks`)

`./check.sh` runs everything a CI would, scoped to what the branch touched, and prints what it
skipped and why. A deploy script refuses what the gate refuses. A check that is flaky is fixed
or deleted the same day; nobody re-runs to see if it passes.

### E8. Fewer, deeper modules; no speculative abstraction
Since 2026-11-25 · Scope: all code · Check: review (the PR names the second caller of every new abstraction)

Build a component, protocol or layer when the second caller exists, not before. Prefer one file
that does one job end to end over five thin layers. Delete dead code in the PR that makes it
dead; a feature flag older than one release is removed or made permanent.

## Part 3. AI routes

### E9. AI proposes; the person accepts
Since 2026-11-25 · Scope: every feature where a model changes user data · Check: an engine test that a model output only creates a proposal; an injection fixture (instructions inside an imported PDF or email) changes nothing before acceptance

A model never writes to the person's data directly. It returns a typed proposal: what changes,
the source it read, and its confidence. The person accepts, edits or rejects; an accepted
change has Undo. Text inside an imported file is evidence, never an instruction.

### E10. Every AI route has an eval, a budget and a fallback
Since 2026-11-25 · Scope: every model call in a product · Check: model ids appear only in the routing file; every route in it has an eval set under `evals/` (or the product's equivalent) and a test of its no-network path

One client, one routing file with the model per route and the reason beside the id. Each
route has a small eval set built from real, scrubbed cases, run before a model or prompt change
(POLICY §1: benchmarks, then a 7-day canary). Each route has a cost ceiling per call and a
behaviour with no key and no network: the app works fully without AI.

### E11. Latency is a feature: the first useful pixel before the model answers
Since 2026-11-25 · Scope: chat, intake, any AI surface · Check: the route's eval records p50 and p90 latency; the UI test asserts a placeholder state within 100 ms

Stream, or show the local part of the answer first (what the engine already knows), then the
model's part. A spinner with no content for more than a second is a bug.

## Part 4. Privacy and speed

### E12. Data is shown by role, and the gate proves it
Since 2026-11-25 · Scope: shared data, exports, public links, AI context · Check: a leak test per role over a fixture: a viewer's payload holds no field marked private (price, references, notes, codes)

Every field has an audience: owner, editor, viewer, follower, public. The server filters by
role; the client never receives what it must not show. AI prompts get the same filtered view.
Secrets live in the provider's store or the accounts hub, never in a repo, a device or a log.

### E13. Performance has a budget, and the budget is a ratchet
Since 2026-11-25 · Scope: the primary platform · Check: `./check.sh perf` (or the product's probe) records app size, cold start and the slowest screen; each may only grow with a reason in the PR

Pick three numbers per product and write them down: download size, cold start to first
content, and the frame time of the heaviest screen. Measure them on the owner's device class.
A regression past the budget blocks the release, not the PR.

## Part 5. Knowledge

### E14. Docs describe today; decisions keep their history
Since 2026-11-25 · Scope: every repo · Check: `teyla docs check`; `teyla ux check` keeps DESIGN.md under 100 lines

A doc says what is true now and is rewritten in place. Why it became true goes into
`docs/decisions/` or the PR. A rule an agent learned from a correction goes into the repo
(`.claude/rules/`, `DESIGN.md`, this file's product twin) the same day, not only into an agent's
memory: memory is not read by the next harness.

### E15. Features have anchors; nothing leaves silently
Since 2026-11-25 · Scope: every product with users · Check: a feature list with one anchor per user-visible feature, and a gate that fails when an anchor's code is gone

A user-visible feature is removed only with the owner's yes, quoted in the PR. Moving one
changes its line.

## Retired or advisory

Not counted toward the 15.

- **Strings are data, not code.** UI text lives in the string catalog; a test fails on a
  hard-coded user-visible string in a view. (advisory, since 2026-11-25)
- **Make the second platform cheap, not early.** Parity follows the primary build reaching a
  person (POLICY §14). (advisory, since 2026-11-25)
