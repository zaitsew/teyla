# Privacy: every call that leaves your machine

Teyla reads your session logs, your repos and your config on your Mac. It has no server, no account,
no telemetry and no analytics SDK. It never uploads a transcript. Nothing about your sessions leaves your Mac unless you turn on a feature that says so; today
that is one row (14, the model brief and ask triage), off by default.

It does make the calls below. Each row names the command that triggers it, the host, what is sent,
and whether it runs without you asking. "Default on" means it runs with a stock install and no flag.

**One switch closes most of them.** `teyla config set safe.enabled=true` (or `TEYLA_SAFE=1`) is safe
mode: every row marked "safe mode: closed" stops, and a command you type by hand can open one call
with `--allow-network`. The gate is `src/teyla/net.py`.

## The MCP server

`teyla mcp` (with no subcommand) talks to an MCP client over stdio. It opens no socket and makes no network call itself. Its tools
run commands listed above: `teyla_routines` is row 7, and `teyla_answer` is row 18, so it starts a local `claude` or
`codex` process exactly as `teyla answer` does. `teyla_asks`, `teyla_intent`, `teyla_load` and `teyla_monitor` read
local files only. No tool reaches `--issues`, `--model`, `--share`, `--allow-network` or any other call that
needs a flag. The text it returns goes to the MCP client you connected, under that client's own policy. `teyla mcp probe` is a different command: it is a client, and it is row 32.

## Not a call

`teyla cloud prep` writes a setup script for a cloud sandbox that contains a `curl` line for the `uv`
installer. Teyla does not run it. `teyla start`, `teyla monitor`, `teyla advise` and `teyla doctor`'s
checks other than row 1 read local files only. `teyla attention` makes no call either: it runs inside
`net.offline()`, which closes the gate for every reader it borrows (schedules, portfolio, doctor, offers), whatever
safe mode or `--allow-network` say. A source that would need the network is read from its cache and the row says how old
the cache is.

The iPhone app's Lab "Morning post card" drafts on the device (Apple's on-device model or a local rule) and sends
nothing: its answers and drafts stay in the app's own storage, and the LinkedIn and X buttons only hand the text to those
apps, where you post it.

## Usage capture in test builds

This is a call a product's **test build** makes (`packages/review-ios`, `TeylaUsage`), not one the `teyla` command makes. It runs only where
`TeylaReview.isActive` is true: Debug and TestFlight. An App Store build records nothing and sends nothing; `teyla review store-check`
still fails an archive that holds the channel key.

| Trigger | Host | What is sent | Default on |
|---|---|---|---|
| The app goes to the background or comes to the front, and events are waiting | The review channel the build's Info.plist names (`TeylaReviewChannelURL`), `PUT /v1/captures/<batch id>/usage.json`, with the product's channel key | A batch of events (at most 800, under 180 KB): the kind (`session`, `screen`, `action`, `task`, `dead_end`, `repeat_tap`), a time, a screen route, an action id or a task name from the list the app declared, a result word (`done`, `cancelled`, `error`, `undone`, `start`, `success`, `cancel`), a duration in milliseconds, the build number and the design variant switched on. The batch also names the app (bundle id, version, build, product slug, `testflight` or `debug`), the declared id lists, and a random id made for this install. Never text a person typed, a title, a name, a contact, a location, the vendor id, the advertising id or the device name. No third-party SDK. | The owner's device (paired with the owner's Mac) sends on its own. Any other tester sends only after one notice, once per install: "Allow" sends, "Not now" deletes what was recorded and sends nothing, ever. A build with no channel configured sends nothing. |

A product with its own backend sets `TeylaReview.configure { $0.deliverUsage = ... }` instead: the batch (the same bytes, no channel key) goes to the
product's server through the product's own closure, and the Info.plist channel is not used. That call is the product's, not Teyla's, and adds no outbound
call to the `teyla` command. The product's backend sees the account that uploaded, so the product's privacy text must say whether it stores it
with the batch. On the Mac, `teyla review pull --vouched-folder DIR` reads a local folder and makes no call.

On the device the events sit in a ring buffer in the app's Application Support folder (at most 5,000 events or 1 MB; the oldest go first) until a send
is allowed. The server copy goes when the Mac's next `teyla review pull --channel` collects it, within the hour; the Mac keeps events for 180 days.
